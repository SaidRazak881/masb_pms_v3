## 3. Import/commit wiring gap — **[GPT: build the missing step]**

The library has parsers, staging, matching, exceptions, and commit/rollback, **but
the pipeline is not wired end-to-end through a route**:

- `importInvoiceWorkbook` / `importQuotationWorkbook` / `importCostOfSalesWorkbook`
  → stage rows with `matching_status = 'PENDING'`, `target_table = null`,
  `target_record_id = null`, `metadata = {parser, error_message, warning_message}`.
- `commit_import_batch()` (SQL, 0004) **only processes** staging rows where
  `validation_status = 'VALID'` AND `matching_status in ('EXACT','ALIAS','COMPOSITE','FUZZY_REVIEW')`
  AND `target_record_id IS NOT NULL` AND `target_table IN ('quotations','invoices','cost_of_sales')`.
- There is **no API route** that calls `matchImportStaging()` +
  `persistMatchingResults()`, and **no step that sets `target_table`/`target_record_id`**.
  Therefore, in the current flow, nothing ever becomes committable.

**Recommended flow for GPT to add** (either as a Node route or a Supabase Edge
Function / DB job):
1. `POST /api/import/[batchId]/match` →
   run `matchImportStaging` → `persistMatchingResults` → marks rows with enum
   status and metadata, and (for candidates) picks `target_table` + `target_record_id`.
2. `POST /api/import/[batchId]/commit` already exists (`app/api/import/commit/route.ts`)
   and calls `commit_import_batch` RPC. It works *once* rows are matched/staged with a target.
3. `POST /api/import/[batchId]/exceptions` already exists and surfaces
   `UNMATCHED` / `DUPLICATE` / validation errors.

Also note: `cost_of_sales` staging rows need a match step that links them to an
invoice by `invoice_number` and sets `target_table = 'cost_of_sales'` +
`target_record_id` (the invoice id), otherwise `commit_import_batch` skips them.
